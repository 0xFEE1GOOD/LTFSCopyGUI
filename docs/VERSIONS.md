# LTFSCopyGui2NAS versions

LTFSCopyGui2NAS and LTFSCatalog always carry the same version, set in one place: `Common\AppVersion.vb`.
Every version pushed to GitHub adds 0.001 (2.000, 2.001, 2.002 ...) and gets a line here.

LTFSCopyGui2NAS (branch ltfscopygui2nas) starts from LTFSCopyGui2 1.011 (branch smallfile-upstream, which
continues on its own). The 1.0xx lines are the history it inherits.

| Version | Date | Changes |
|---|---|---|
| 1.001 | 2026-11-14 | First LTFSCopyGui2 version: this branch of LTFSCopyGUI 3.6.0 with the upstream build number and the "Non-commercial License" title text removed. Includes the work on this branch so far: small-file writing, restore read-ahead, LTFSCatalog with restore hand-off, the Segoe UI facelift, and the usability changes (labelled status lights, steady I/O light, keyboard shortcut windows, menu items that open the other app). New tapes record LTFSCopyGui2 1.001 in the index creator and in the cartridge memory application name/version. |
| 1.002 | 2026-11-14 | Restore no longer stops with "Illegal characters in path". Cause: the index writer put a line break before a name that starts with ' &amp; &lt; &gt; or " (inherited from upstream LTFSCopyGUI 3.6.0; affects tapes written by it and by 1.001). The writer is fixed, and restore (folder, selected files, catalog hand-off, extract as empty files, delete disk files by index) drops line breaks at the ends of a name and replaces characters Windows rejects with _ (logged as "Name changed for Windows"). Each new index generation now records the program that wrote it (it kept the creator of the first index). |
| 1.003 | 2026-11-14 | Device configurator, TapeAlert Response log page (12h): every flag was labelled one number too low (a "Flag 00h" existed and 40h was missing), so e.g. the bit shown as "31h Diminished Native Capacity" was really 32h Lost Statistics. Labels now start at 01h, in the code and in the shipped logpages\0x12.xml. The TapeAlert log page (2Eh) was already right. |
| 1.004 | 2026-11-14 | Restore reports failures honestly. Restoring files, a folder or an LTFSCatalog request no longer ends green "Restore finished" when some files could not be restored: the light goes red and a message gives the count (the log lists the files). A read error on a small file (one that fits in one tape record, e.g. packed files) now asks Abort/Retry/Ignore like larger files instead of stopping the whole restore; Ignore skips the files of that record and asks once. A target file that is open in another program or access-denied fails only that file. "Decompress index" no longer drops the folder from the index when the archived index cannot be read back. "Move to index partition" moves only files read back whole, frees the drive and window after Cancel, and ends red when a file failed. |
| 1.005 | 2026-11-14 | "Delete disk files by index" is now "Delete disk copies of these tape files…": it asks first, deletes a disk file only when its path, size and modified time match the tape file (it used to check size only), logs every deleted and kept file, never creates folders and no longer reserves the drive. Restore names: trailing dots and spaces and Windows device names (CON, NUL, COM1, LPT1 …, also "nul.txt") are made safe ("NUL_.txt"); two tape names that become the same Windows name get "name (2).ext" instead of stopping the restore (verify and delete use the same names). A restore copies a deduplicated file from its first copy on disk instead of reading (and seeking back over) the same tape records again. Index: names are percent-decoded only when the index marks them percentencoded="true" (LTFS spec); "%25" in a plain name is no longer turned into "%" on load (folder names used to lose one "%25" per index generation); names with control characters are written percent-encoded. An index whose data placement policy or folder extended attributes hold &amp; &lt; &gt; ' " no longer fails to load, and both, with any other index part this program does not use, are written back unchanged in the next index generation (they were dropped). Block packing: no list scan per file. |
| 1.006 | 2026-11-14 | LTFSCopyGUI command bar: Force Eject now comes before Safe Eject (Safe Eject ends the bar). Main window, Other Tools: the LTFSConfigurator button had a smaller font than Index Analyzer and the others because its caption did not quite fit and it had no free space beside it; buttons side by side now share one font size (shared LTFSCopyGUI/LTFSCatalog style): when a caption in a row does not fit, the row is laid out again with each button as wide as its caption needs, and when the row is too short for that at 10 pt, all its buttons step down together (that row is 9.5 pt, evenly spaced). |
| 1.007 | 2026-11-14 | Writing: small files (under 16 KiB) are read ahead into memory again, so the drive no longer waits on the source (a NAS: one network round trip per file) for each of them. The read-ahead had stopped after a few files in every write since upstream LTFSCopyGUI 3.6.0 ("small-file preload failed: Collection was modified" in each writer log) because it walked the file list while the writer cleared finished entries from it. It now reads only files the writer has not reached yet, holds at most the configured file count and 256 MiB, and leaves any file it cannot read to the writer, which retries and reports it as before. Device configurator: closing the window while a load, eject or unthread was still running no longer logs that command as failed (it worked; only the result could not be shown in the closed window). |
| 1.008 | 2026-11-14 | Protection for a tape whose index partition is out of date. That happens when a tape leaves the drive after a write but before Safe Eject (eject button, power cut, crash): the newest index is then only at the end of the data partition, and a normal load reads the older one from the index partition. Before, a write with that older index started right after its copy on the data partition and overwrote everything written later (inherited from upstream LTFSCopyGUI 3.6.0). Now (1) after loading, the program compares the cartridge memory's volume change reference with the one recorded at the last index partition update; when they differ it says so and offers to read the newest index from the data partition (Tape > Index > Read from data partition); (2) before writing with an index loaded from the index partition, it checks that the data partition ends right after that index's copy; if more data follows, nothing is written and a message explains what to do. |
| 1.009 | 2026-11-16 | Writing waits for a full buffer. The tape now starts only when the read-ahead buffer is full (or already holds everything left to write): before, it started on the first file and then stopped and restarted the tape while a slower source (a NAS) caught up. The buffer fills while the tape is being positioned; the status bar shows its level, and the writer log gets one line on how full it was and how long that took. When the buffer runs empty during a write, the tape waits until it is full again for small files too (before, only files larger than one tape block, 512 KiB, waited, and only until 75 %). The wait also ends when the source has added nothing for 30 s (was 10 s), on Stop, or with Test > Stop waiting for buffer. Both follow the existing setting LTFSWriter_WaitOnBufferEmpty. The buffer size is now entered and shown in GiB, both in the File buffer menu item and in the settings window: 4, 0.5 or 512 MiB; a plain number is GiB, allowed from 16 MiB to half of the computer's memory. It is still stored in bytes, so existing settings keep their value. |
| 1.010 | 2026-11-19 | Writing reads the source faster. Files of 16 MiB or more are read in 8 MiB chunks over 4 handles at once (passed on in order), and files under 1 MiB are read ahead by 4 workers instead of 1 (the limit was 16 KiB). From a NAS over 10G (Synology DS3615xs, cold files): large files 276 → 470-495 MB/s, the slowest second 165-188 → 318-402 MB/s, so the source can keep the tape at full LTO-7 speed (300 MB/s); folders of ~140 KB files 34 % more files per second. New setting LTFSWriter_ParallelSourceReads (default 4, at most 8; 1 = one read at a time as in 1.009). Memory: 4 × 8 MiB for the large-file chunks, reused for the whole write. |
| 1.011 | 2026-11-19 | Writing from a NAS: source files are read over several network connections. A Samba NAS (here a Synology) serves each connection with one process that reads one file at a time, so the 4 read-ahead workers of 1.010 only queued behind each other on folders of office files (the 8 GiB buffer emptied in a minute and took 96 s to refill at ~85 MB/s). Windows opens one connection per server name, so reads now go over the server's other names too (new setting LTFSWriter_SourceServerAliases, default auto: e.g. 192.168.3.5 also as LinkBigNas.local and LinkBigNas; a name is used only once the share answered under it; empty = one connection; more names can be added in the hosts file). Read-ahead now covers files under 16 MiB (was 1 MiB); larger files go over the names in turn. When the writer reaches a file a worker is still reading, it waits for that read instead of reading the file again. Cold office-type folders on the NAS: 93 files/s with one reader, 117 with 4 workers (1.010), 166 with 4 workers over 3 connections. |
| 2.000 | 2026-11-19 | First LTFSCopyGui2NAS version: a separate line for writing from a NAS, started from LTFSCopyGui2 1.011 (branch smallfile-upstream stays as it is). The program is the same as 1.011; only the name changes: window titles, the keyboard shortcut window, LTFSCatalog's texts, the installer (own AppId, installs to C:\LTFSCopyGui2NAS beside LTFSCopyGui2) and new tapes, whose index creator and cartridge memory application name/version record LTFSCopyGui2NAS 2.000. |
| 2.001 | 2026-11-19 | Adding a folder is faster, most of all from a NAS: each file's size and times are taken from the folder listing, and .xattr sidecar files are found in it too, instead of asking the server about every file three more times (a 7,126-file folder on the NAS with a warm cache: 0.61 -> 0.16 ms per file). The queued names, sizes, times and extended attributes are the same as before (compared file by file). Files whose path is longer than 260 characters can now be added and written from a network path (\\server\share\...): before, each such file showed an error and was left out of the write (paths through a mapped drive letter already worked). |
| 2.002 | 2026-11-19 | LTFS NAS Reader: a DSM package for the Synology (NasReader\, built by CI as LtfsNasReader-2.002-1.spk). It reads the files of a write on the NAS itself, 16 at once, and sends them to the app in write order, instead of the app reading every file over SMB. Install it with Package Center > Manual Install, give its user sc-ltfsnasreader Read only on the shares you write from, then set LTFSWriter_NasReader (the NAS address, e.g. 192.168.3.5) and LTFSWriter_NasReaderKey (the key on the package's page in DSM). Folders are still added over the share, so the tape index is unchanged. Any file the NAS cannot send (not found, read error, share it does not know, lost connection, wrong key) is read over the share as before; a large file continues from the byte where the NAS stopped. Cold office folder on the NAS (7,126 files, 5.9 GB): 132 MB/s, 159 files/s with the 1.011 reads over SMB; about 500 MB/s, 600 files/s through the reader, no second under 300 MB/s. A 28 GB slice of larger files: 332 -> 472 MB/s. The package's page shows the current write, how busy each disk is (with a warning while a RAID check or resync runs), which shares it can read, recent writes, its settings and the key. Not tested with the tape yet. |
| 2.003 | 2026-11-19 | After the first tape test with the NAS reader. LTFS NAS Reader package (LtfsNasReader-2.003-1.spk, install it over 2.002): the file being sent no longer reads ahead without a limit. When the tape side is slower than the NAS (most of a write), 2.002 could hold a whole large file in the NAS's memory (test: 2,000 MiB held with a 64 MiB read-ahead, now 72 MiB); the likely cause of the slow stretch after a 14.7 GiB .pst in that write. Large files are read in 8 MiB pieces by several readers at once (two cold .pst files through the reader: 513 -> 564 MB/s). The sender no longer waits on the network while holding the readers' lock. The NAS log gets a line every 10 s per write with the rate and what the NAS waited for (its disks or the app), and the page shows the same. The page no longer cuts off the Shares list (two columns, one on narrow windows). App: a NAS light in the status line (blue = LTFSWriter_NasReader is set and the reader answers and accepts the key; grey = off; red = not ready, the tooltip says why and which shares it can read; checked every 20 s and when clicked). The writer log gets a "Source progress" line every 10 s (MB/s, files/s, and how long reading waited because the buffer was full, i.e. for the tape side). The ~20 "Buffer refilled ... (it holds all the rest)" lines at the end of each write are gone. Not tested with the tape yet. |
| 2.004 | 2026-11-20 | After the second tape test with the NAS reader (2.003). The NAS stayed ahead of the tape for the whole write (its log: waiting for the app, read-ahead full), and the second job took 261 s instead of 323 s (tape at full speed 85 % of the time, was 69 %). The remaining stops were the drive's own: when data arrives slower than it could write it, the drive drops to a slower speed and later stops for about 4 s to speed up again. On big files the writer gave the drive only 350-385 MiB/s. With "Calculate checksum async" on, each WRITE still waited until the hash thread had finished the previous block (the hash thread held the lock that queuing a block needs), so every 512 KiB block cost the SCSI time plus the SHA-1 time (SHA-1 takes 1.1 ms per block on this CPU's E-cores). Queuing now takes only the queue's own lock. In a no-tape test of the writer's block pipeline against a simulated drive at 472 MiB/s: 373-402 -> 428-433 MiB/s, SHA-1 unchanged. The drive can then stay at full speed on data up to about 1.5:1 compression (was about 1.3:1). The writer log gets a line for every WRITE the drive held 1 s or more ("Drive held a WRITE for 4.1 s: the tape stopped ...") and one per write with the total. The NAS package is unchanged (2.003 stays installed). Not tested with the tape yet. |
| 2.005 | 2026-11-20 | After the third tape test with the NAS reader (2.004, both folders in one write, 63,408 files, 114.9 GB): 8:36, slower than the 2.003 test (7:05 for the same files in two writes). The drive stopped only 5 times (12.9 s), and the NAS was ahead except for about 30 s of cold small files, but the drive ran at its lower speeds for most of the write with the source buffer full: about 180 MiB/s on tape for 2 minutes, its slowest speed (about 93 MiB/s) for the whole of YS_Intega.pst (81 s, was 32 s), and about 162 MiB/s for 2 more minutes; full speed came back only after a stop. That log cannot show whether the drive or the app set that pace (the buffer is full either way), so the writer now logs every 10 s the time spent inside WRITE commands (the drive) and outside them (the app), the data rate, the deepest checksum queue and how long WRITEs waited for it. No change to what is written. Not tested with the tape yet. |
| 2.006 | 2026-11-20 | Restore: the drive stopped and changed speed during a restore of the 63,408-file write (writer-5611ac52.log) although the 8 GiB read-ahead never filled, so the reading side was the limit. (1) The reader copied every record into a new array (512 KiB, on the large object heap): .NET ran 1,137 full garbage collections in 7 minutes, which hold up the reading thread. Record buffers now come from a pool and are given back once the restore has written them; a record carries its length, since the buffer can be longer. (2) The reader read through gaps of up to 64 records and positioned the tape (LOCATE) past anything longer; the index a write leaves in the middle of the tape every 36 GiB is about 160 records for 60,000 files, so each one stopped the tape. It now reads through gaps of up to 2048 records (2-3 s of reading). (3) The restore log gets the read-side timing that writes have had since 2.005: every 10 s the time inside READ (the drive) and outside (the app), the read-ahead fill and the full GCs, a line for each READ held 1 s or more, and the total at the end. New no-tape test tools\imgrestore: synthetic files on the virtual tape, the real restore engine, every file checked byte for byte. Not tested with the tape yet. |
| 2.007 | 2026-11-20 | Fixes from a review of the NAS line (2.000-2.006). (1) A small file that grew after the list was made went to tape cut to its listed length when read through the NAS (over the share the write reports "Source file length changed"): the app now asks the NAS for one byte more than listed, and a file that comes back longer is read over the share, which reports it as before; works with the 2.003 package too. (2) After a lost NAS connection the small-file read-ahead had already skipped the files the NAS was to send, so they were read one by one; it now starts again from there. (4) The drive-stall and write-time counters are kept per drive and removed after the write, so two writer windows no longer mix them and a closed window is not kept in memory. (5) The NAS summary line is logged once (was twice), and after a lost connection it says how many files went over the share. (6) A NAS that takes the connection but hangs holds up the start of a write 5 s instead of 30 s before the share is used. (7) The NAS light checks every 10 minutes after the NAS refused the key (each check adds a "wrong key" event on the NAS page) and not during writes. (8) An IPv6 address in LTFSWriter_NasReader is read correctly.
